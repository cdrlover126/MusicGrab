# 第二款工具：视频 → 文档（字幕 / 转写 / Markdown / PPT）技术方案

- 版本：v0.1（方案稿，未进入编码）
- 日期：2026-11-09
- 关联项目：MusicGrab（乐取 MusicGrab）v1.8.0
- 结论先行：**可行**，但四项能力成本相差一个数量级；建议按「字幕 → Markdown → 转写 → 文档导出」分阶段做，**独立成第二款工具**，与 MusicGrab 共用组件底座。

---

## 1. 背景与动机

MusicGrab 已经把「链接 → 音轨 → MP3」的整条链路跑通了，包括：多平台解析、路由与代理、批量调度、组件自愈、拖放导入、转换报告。工程底座是现成的。

用户提出的四个诉求，本质是同一条流水线的**下游延伸**：

```
链接 ──► 音轨 ──► MP3            ← 今天做到这里
      └─► 视频 ──► 字幕/转写 ──► Markdown ──► PPT/PDF/DOCX
```

关键认知（写给未来的自己）：

1. **「能抽 MP3」不等于「能下载完整视频」**。现在走的是 yt-dlp 的 `bestaudio`，**视频流根本没下载过**。要产出视频必须改成 `bestvideo+bestaudio`，流量/磁盘是几十倍量级的差别。
2. **「提取字幕」和「识别内容」是两件事**。前者是站点**已经提供了文字**，后者是音频里**没有文字、要靠模型听写**。前者近乎免费，后者是真正的重资产。
3. **「转 Markdown」很便宜，「转 PPT」取决于排版引擎，「转 PDF」取决于是否要引入 LaTeX**。PPTX/DOCX 可以纯 Python 离线做，PDF 要么纯 Python 自己排版，要么引入外部二进制，要么交给用户自己导出。

## 2. 产品定位

### 2.1 一句话定位

> **乐取 Note**：把公开视频/音频的内容，变成可读、可搜、可复用的文档（字幕 / 转写稿 / Markdown / PPT）。

### 2.2 目标用户与场景

| 用户 | 场景 | 需要的能力 |
|---|---|---|
| 自媒体/做笔记的人 | 收藏的教程视频 → Markdown 笔记 → 稍后阅读 | 字幕 / 转写 → Markdown |
| 学生/研究者 | 课程/讲座录屏 → 讲义或复习提纲 | 转写 → Markdown → DOCX/PDF |
| 会议/直播回放 | 直播录像 → 会议纪要初稿 | 转写（长音频分段）→ Markdown |
| 讲师/培训师 | 自己的课程视频 → 配套 PPT | 转写 → 大纲 → PPTX（**注意：这一档需要 LLM，见 §9 不做清单**） |

### 2.3 明确不做

- 不做「批量搬运视频到文档」的搬运工坊（版权风险，见 §8.3）
- 不做内容二次分发、破解 VIP、去水印
- 不做云端账号体系（保持单机、免登录、可离线）

## 3. 产品形态：独立第二款工具（已决策）

### 3.1 为什么不并进 MusicGrab

| 维度 | 独立工具 | 并入 MusicGrab |
|---|---|---|
| 主包体积 | 各自轻量（Note 基础包约 40–60MB） | 变成 250MB+ 的胖包，车机用户买单 |
| 用户心智 | 「听歌的」和「做笔记的」是两类人 | 一个界面塞两套场景，选项页膨胀 |
| 迭代节奏 | Note 可以两周一个大版本 | 每次改动都要重新验证 MusicGrab 全流程 |
| 许可边界 | GPLv3（ffmpeg）问题只影响需要 ffmpeg 的功能 | 闭源分发已因 ffmpeg 受限，再加 pandoc 会更难看 |
| 组件底座 | **共用**（见 §3.3），不重复安装 | —— |

### 3.2 仓库结构（建议）

保持**同一个仓库、两个可执行产物**，避免两套代码各自腐化：

```
douyin-mp3/                 # 现有仓库
├─ douyin_mp3/              # MusicGrab 应用 + 共享底座（保持不动，作为公共层）
├─ note_mp3/                # 新增：第二款工具（独立版本号，如 v0.1）
│  ├─ __init__.py
│  ├─ cli.py                # 命令行入口
│  ├─ gui.py                # GUI
│  ├─ pipeline.py           # 编排：取流 → 字幕/转写 → md → 导出
│  ├─ subtitles.py          # yt-dlp 字幕拉取 + srt/vtt 解析
│  ├─ asr.py                # faster-whisper 封装（模型按需下载）
│  ├─ markdown_writer.py    # 统一 Markdown 产出
│  ├─ exporters/
│  │  ├─ docx_writer.py     # python-docx
│  │  ├─ pptx_writer.py     # python-pptx
│  │  └─ pdf_writer.py      # reportlab 或 HTML
│  └─ models.py             # 数据结构（Note/Segment/Chapter）
├─ packaging/               # 两套打包脚本（note_exe.ps1）
└─ docs/design/             # 本方案所在
```

> **共享层约定**：`note_mp3` 直接 `from douyin_mp3.updater import ...` 等方式复用
> `updater / tls / proxy / dragdrop / local_media / converter / config`，
> **不要复制粘贴**。MusicGrab 侧不做破坏性重构（不改名、不移动模块），
> 避免影响已发布版本。

### 3.3 组件底座复用（关键设计）

MusicGrab 已经有成熟的「组件自愈」机制，直接复用：

| 机制 | 位置 | Note 如何用 |
|---|---|---|
| 组件根目录（便携 + 机器级双位置） | `updater.component_locations()` | ffmpeg / yt-dlp **共用同一份**，不重复下载 |
| 版本自描述（`version.txt`） | `updater` | 组件"是不是最新版"判断直接复用 |
| 覆盖层 `state.json` | `%LOCALAPPDATA%\MusicGrab\` | Note 用自己的 `state.json`，不污染 MusicGrab 的 |
| 按需安装 + SHA256 校验 + 失败回滚 | `updater.install_*` | 新增第三类组件：**ASR 模型** |
| CA 证书兜底 | `tls.py` | 原样复用 |
| 拖放导入 | `dragdrop.py` | 原样复用（支持拖链接/拖文件） |

**目录建议**：

```
%LOCALAPPDATA%\MusicGrab\          ← 机器级共享组件（ffmpeg / yt-dlp，Note 只读复用）
%LOCALAPPDATA%\MusicGrabNote\      ← Note 私有（state.json、ASR 模型缓存、设置）
<exe 同级>\MusicGrab_components\    ← 便携组件（Note 同样识别）
<exe 同级>\MusicGrabNote_models\    ← 便携模型（可选）
```

> 组件目录**只读复用**是安全的：ffmpeg / yt-dlp 都是无状态二进制，
> 不写注册表、不写配置。多进程并发调用同一份 yt-dlp 也没问题。

## 4. 能力拆解与技术选型

### 4.1 能力矩阵

| # | 能力 | 技术方案 | 新依赖 | 体积 | 工作量 | 依赖关系 |
|---|---|---|---|---|---|---|
| C1 | 完整视频下载（副产物） | yt-dlp `bestvideo+bestaudio` + ffmpeg 合并 | 无 | 0 | 0.5 人日 | 独立 |
| C2 | 提取字幕 | yt-dlp `writesubtitles` / `writeautomaticsub` | 无 | 0 | 0.5 人日 | 独立 |
| C3 | 字幕 → Markdown | 自写 srt/vtt 解析 + 模板 | 无 | 0 | 0.5 人日 | C2 |
| C4 | ASR 转写 | faster-whisper（本地 int8） | `faster-whisper` + 模型 | 75MB–3GB（按需） | 2–3 人日 | 独立 |
| C5 | 转写 → Markdown | 分段 + 说话人切分（VAD）+ 模板 | 无 | 0 | 0.5 人日 | C4 |
| C6 | Markdown → DOCX | `python-docx`（MIT） | 纯 Python | <2MB | 0.5 人日 | C3/C5 |
| C7 | Markdown → PPTX | `python-pptx`（MIT） | 纯 Python | <2MB | 1–1.5 人日 | C3/C5 |
| C8 | Markdown → PDF | `reportlab`（BSD）纯 Python / HTML 兜底 | 纯 Python | <3MB | 1 人日 | C3/C5 |
| C9 | 一键导出 Word/PDF（外部引擎） | `pandoc`（GPL-2.0，~35MB，组件化按需下载） | pandoc 二进制 | 35MB | 0.5 人日 | 可选增强 |

### 4.2 C1 完整视频下载

```python
opts = {
    "format": "bestvideo+bestaudio/best",
    "merge_output_format": "mp4",
}
```

要点：

- 合并依赖 ffmpeg（已有）；`merge_output_format` 固定 mp4 避免 mkv/webm 兼容问题
- **体积**：1080P 常见 300–800MB/条 → 必须做成**显式开关**，默认关闭
- 已知限制：内置 ffmpeg 缺 `mpegps` 解复用器 → **VOB 不支持**（与 MusicGrab 现状一致）
- 建议产物目录与音频分开：`输出/音频/`、`输出/视频/`

### 4.3 C2 提取字幕（yt-dlp 原生能力）

```python
opts = {
    "skip_download": True,
    "writesubtitles": True,        # 人工字幕
    "writeautomaticsub": True,     # 自动字幕
    "subtitleslangs": ["zh-Hans", "zh-CN", "zh", "en", "en-US"],
    "subtitlesformat": "srt/vtt/best",
}
```

**平台覆盖矩阵**（务必在 UI 里如实告知用户，否则会被当 bug）：

| 平台 | 人工字幕 | 自动字幕 | 备注 |
|---|---|---|---|
| YouTube | ✅ 常见 | ✅ 几乎都有 | 覆盖率最高 |
| B站 | ⚠️ 部分视频有 CC | ⚠️ 少 | 多为 UGC 方自备字幕 |
| 微博/网易云等 | ❌ 基本无 | ❌ | 无字幕轨 |
| 抖音/快手/酷狗 | ❌ | ❌ | 平台不提供 |
| 播客/音频站 | ✅ | ✅ | RSS 自带 |

> 结论：**C2/C3 的价值集中在 YouTube / B站 / 播客**，
> 中文短视频平台基本用不上 —— 这是"独立第二款工具"的最强论据。

**命名与存放**：`{index:03d}_{title}.zh-Hans.srt`，与音频同目录或独立 `字幕/` 目录（建议独立目录，避免与播放器按扩展名混淆）。

### 4.4 C4 ASR 转写（真正的重头）

**选型**：

| 方案 | 许可 | 模型体积 | 速度（现代 CPU int8） | 隐私 | 结论 |
|---|---|---|---|---|---|
| faster-whisper（本地） | MIT（依赖 CTranslate2，MIT） | tiny 75MB / base 145MB / small 480MB / medium 1.5GB / large 3GB | base ≈ 5–10× 实时，small ≈ 2–4×，medium ≈ 1×，large < 1× | ✅ 全离线 | **推荐** |
| openai-whisper（官方） | MIT | 同上 | 慢 2–4× | ✅ | 备选（体积小些？否） |
| 云端 ASR（各家 API） | 商用条款 | 0 | 快 | ❌ 音频上传 | 仅作为可选「高质量模式」，默认关闭 |

**模型分发方案**（复用组件自愈机制）：

```
<组件目录>/models/whisper/small/     # 模型文件
<组件目录>/models/whisper/small/version.txt   # {"model": "small", "sha256": ..., "size": ...}
```

- 用户在设置里选档位 → 首次使用提示"需要下载模型（480MB）"→ 走现有 updater 的
  「下载 → SHA256 校验 → 解压到覆盖层 → 生效」流程
- **模型与程序解耦**：程序升级不会动模型，模型升级也不需要重装程序
- 量化：int8 量化后体积约为原版 1/3，精度损失对"听清内容"场景可接受

**转写工程要点**：

1. **长音频分段**：用 VAD（`faster-whisper` 内置 silero VAD）切静音段，
   按 30–60s 窗口拼接，避免一次喂几小时的音频
2. **进度与取消**：按片段回调进度（GUI 进度条 + 取消按钮），单段失败可重试
3. **时间戳**：保留 segment 级起止时间 → 直接产出 SRT，再统一转 Markdown
4. **说话人分离**：diarization（pyannote）需要额外模型 + HF token，**本阶段不做**
5. **中英混说**：whisper 的 language 参数留 `auto`，自动检测；允许手动指定
6. **术语表/提示词**：`initial_prompt` 可注入专有名词（如人名、缩写），成本为零、收益明显

### 4.5 C3/C5 Markdown 产出

统一模板（字幕与转写共用）：

```markdown
---
title: "标题"
source: "https://www.bilibili.com/video/BV..."
author: "UP 主人"
duration: "12:34"
platform: "bilibili"
captured_at: "2026-11-09T20:11:03+08:00"
captions: "subtitle"      # 或 "asr"
---

# 标题

> 来源：<https://...> ｜ 作者：xxx ｜ 时长：12:34 ｜ 来源类型：官方字幕

## 正文

**[00:00]** 第一段文字……

**[00:32]** 第二段文字……

## 章节（可选）

- [00:00] 开场
- [02:15] 第一个要点
```

- 段落合并：相邻字幕间隔 < 2s 且未断句 → 合并成一段（否则全是碎行）
- 章节切分：优先用平台自带章节（yt-dlp `chapters` 字段）；没有则按时间间隔启发式切
- 输出编码 UTF-8，文件名做非法字符清洗（复用 `converter.sanitize_filename`）

### 4.6 C6/C7/C8 文档导出

| 目标 | 选型 | 做法 | 备注 |
|---|---|---|---|
| DOCX | `python-docx`（MIT） | 标题 → Heading 1/2/3；`**[00:00]**` → 加粗正文 | 最省事，Word 里再导出 PDF |
| PPTX | `python-pptx`（MIT） | 章节 → 一页一张；正文 → 要点列表 | 需要规则化排版（自动分页、超长截断） |
| PDF | `reportlab`（BSD） | 中文需注册 TTF（思源黑体，OFL，体积 8–16MB） | 排版要自己调；或走 HTML + 浏览器打印 |
| PDF（增强） | `pandoc`（GPL-2.0） | 组件化按需下载，走现有 updater | 排版最好看，体积 +35MB |

**CJK 字体是 PDF 的隐形坑**：reportlab 默认字体不含中文，必须内置一份 OFL 字体
（思源黑体/Noto Sans CJK），否则全是方框。这条要写进排期，别等 QA 才发现。

**PPTX 的现实评估**：自动排版很难做到"像人做的"。第一版只做
「每章节一页 + 要点列表 + 底部时间戳」，别追求设计感。

## 5. 架构与数据流

```
                    ┌──────────────────┐
   链接/拖放 ───►   │  输入适配层       │  ← 复用 douyin_mp3.dragdrop / parser
                    └────────┬─────────┘
                             ▼
                    ┌──────────────────┐
                    │  取流层           │  ← yt-dlp（共用组件）
                    │  音频 / 视频 / 字幕 │
                    └────────┬─────────┘
                             ▼
        ┌────────────────────┴────────────────────┐
        ▼                                         ▼
  ┌───────────┐                          ┌──────────────┐
  │ 字幕轨     │（有则用）                 │ ASR 转写      │（无字幕时兜底）
  │ srt/vtt   │                          │ faster-whisper│
  └─────┬─────┘                          └──────┬───────┘
        └──────────────┬───────────────────────┘
                       ▼
              ┌────────────────────┐
              │  Markdown 产出层    │  ← 统一模板（§4.5）
              └─────────┬──────────┘
                        ▼
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
     .md            .docx            .pptx / .pdf
```

**关键设计点**：

1. **字幕优先，ASR 兜底**：有官方/自动字幕就用字幕（快、准、零成本）；
   没有才提示下载模型做 ASR。这条策略决定 80% 的日常体验。
2. **流水线阶段化**：每阶段产出物落盘（`工作目录/01_audio/ 02_subs/ 03_md/`），
   失败可从断点续跑，不必整条重来。
3. **统一 CLI + GUI**：核心逻辑在 `pipeline.py`，CLI 与 GUI 都只是壳
   （与 MusicGrab 的分层一致，保证可脚本化、可批处理）。
4. **复用 MusicGrab 的路由/代理**：境外站点（YouTube）必须走代理，
   `proxy.resolve_route` 直接复用，别重写一套。

### 5.1 CLI 草案

```powershell

note-mp3 models list|download       # 管理 ASR 模型

```

## 6. 体积与分发预算

| 组合 | 基础 exe | 模型（按需） | 合计 | 备注 |
|---|---|---|---|---|
| 最小（字幕 → Markdown） | ~45MB | 0 | ~45MB | 复用 MusicGrab 已有 ffmpeg/yt-dlp 组件，不重复打包 |
| 标准（+ DOCX/PPTX） | ~50MB | 0 | ~50MB | 纯 Python 依赖，体积可忽略 |
| 全量（+ ASR + PDF 中文字体） | ~55MB | 75MB–3GB | 130MB–3GB | 模型按需下载，基础包不膨胀 |
| + pandoc 增强导出 | ~90MB | — | ~90MB | 不推荐默认带 |

**关键**：Note 的 ffmpeg / yt-dlp **不随包分发**，直接从共享组件目录读取
（若用户没装过 MusicGrab，则首次运行时按需安装到共享目录）。
这与 MusicGrab 的"组件自愈"完全一致，**额外分发成本为 0**。

| **M3 ASR 转写** | 模型管理 + 分段转写 + 稿子 | 3 人日 | small 模型下 30 分钟音频 10 分钟内转完且断句可用 |
| **M4 文档导出** | DOCX/PPTX/PDF + 中文字体 | 2 人日 | 三种格式都能打开且中文不乱码；PPTX 分页合理 |
| **M5 视频副产物** | 可选下载完整视频 | 0.5 人日 | 开关关闭时行为不变；开启时能拿到合并好的 mp4 |
| **M6 打包分发** | 独立 exe + 发布包 + 文档 | 1 人日 | 单文件版/目录版各一份，SHA 一致 |

**总计约 10 人日**（不含 M3 的模型分发打磨与 M4 的排版调优，后者浮动大）。

## 8. 风险与对策

### 8.1 技术风险

| 风险 | 等级 | 对策 |
|---|---|---|
| ASR 模型体积劝退用户 | 中 | 默认档位给 base/small 一键切换；下载前明确告知体积与预计耗时；支持断点续传 |
| 平台字幕覆盖率低（抖音/快手无） | 高 | UI 必须**提前说明**"该平台通常没有字幕，将使用 ASR"；不要让用户以为是 bug |
| 长音频内存/耗时爆掉 | 中 | VAD 分段 + 流式产出 + 可取消；模型量化 int8 |
| CJK 字体导致 PDF 方框 | 中 | 内置一份 OFL 中文字体；启动自检检查字体可用性 |
| PPTX 排版难看 | 中 | 第一版只做朴素版式；把"排版"留给后续模板机制 |
| 与 MusicGrab 共享目录产生耦合 | 低 | 组件只读复用；私有数据放 Note 自己的目录；加 doctor 自检 |
| yt-dlp 接口变动 | 中 | 复用现有组件自愈：上游更新自动跟进 |

### 8.2 许可风险

| 组件 | 许可 | 闭源分发的处理 |
|---|---|---|
| faster-whisper / CTranslate2 | MIT | 可闭源分发，需保留版权声明 |
| Whisper 模型权重 | MIT | 同上，模型随下载分发时附许可说明 |
| python-docx / python-pptx | MIT | 可闭源分发 |
| reportlab | BSD | 可闭源分发，保留声明 |
| pandoc | GPL-2.0 | 独立进程调用（IPC）通常不构成衍生作品，**但需显著标注**；建议仅作可选组件，不进基础包 |
| 中文字体（思源黑体） | OFL | 可分发，需保留 OFL 声明 |
| ffmpeg（复用 MusicGrab 组件） | GPLv3 | 与 MusicGrab 现状一致：显著标注 + 提供源码获取方式 |

> 与 MusicGrab 相同：**闭源商业分发 + 内含 GPLv3 ffmpeg 的传染性**是既有问题，
> Note 不新增类别，只在 pandoc 上多一处需要标注。

### 8.3 内容合规

- 字幕与转写稿属于**衍生内容**，个人学习研究可用，**不得公开分发/商业化**
- 工具内保留「仅供个人学习研究」免责声明（与 MusicGrab 一致）
- 不做"一键搬运全网视频变文档"类批量功能宣传
- 云端 ASR 若提供，必须显式提示"音频将上传到第三方"

## 9. 不做清单（本阶段明确排除）

| 项 | 原因 | 何时再考虑 |
|---|---|---|
| LLM 摘要 / 章节提炼 | 需接 LLM（key/联网/成本），且这是"内容理解"而非"内容获取" | 有稳定模型通道后 |
| 自动生成 PPT 大纲 | 依赖上一条 | 同上 |
| 说话人分离（diarization） | pyannote 需 HF token + 额外模型 | 会议场景成为主力后 |
| 视频剪辑 / 抽帧 / 封面图 | 属于视频工具范畴，与本产品定位不符 | 永不做 |
| 多语言翻译 | 需 LLM 或翻译 API | 同 LLM 通道 |
| 云端账号与同步 | 与"单机免登录"定位冲突 | 永不做 |

## 10. 待确认事项（需要拍板）

1. **名字**：建议「乐取 Note / MusicGrab Note」，与「乐取 MusicGrab」成系列。
2. **分发方式**：同仓库两个 exe（CSDN 资源页开两个资源），还是 Note 先只发 GitHub/内网？
3. **是否真要做 ASR**：C1–C3（字幕 + Markdown）成本极低、价值明确，可以**先发**；
   ASR（M3）占了一半工作量且体积劝退，可以先用"外部 ASR 结果导入"顶一顶
   （支持导入现成的 srt/txt，走同一条 Markdown 流水线）。
4. **PDF 路线**：内置 reportlab（可控、纯 Python）还是交给用户用 Word 导出（最省事）？
5. **是否需要 CLI 优先**：如果目标用户是脚本化批处理，GUI 可以延后，M1 + CLI 就能发。

## 附录 B：关键决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 独立工具 vs 并入 | 独立工具 | 体积、心智、迭代节奏；组件底座已可共享 |
| 字幕 vs ASR 优先级 | 字幕优先，ASR 兜底 | 字幕零成本零依赖，覆盖 YouTube/B站/播客 |
| 本地 ASR vs 云端 | 本地（faster-whisper） | 免登录、隐私、可离线；云端仅作可选增强 |
| 模型分发 | 组件化按需下载 | 复用已有自愈机制，基础包不膨胀 |
| PDF 实现 | reportlab + 内置 OFL 字体 | 不引入 LaTeX；体积可控 |
| pandoc | 可选组件，不进基础包 | GPL-2.0 + 35MB，非必要不进包 |
